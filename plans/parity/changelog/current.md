- **Content stream numbers use Java's 4 fraction digits (2026-10-29, test-first)**: every content stream the port generated wrote real numbers with **5** fraction digits, because the three stream classes (`PDPageContentStream`, `PDAppearanceContentStream`, `PDFormContentStream`) hardcoded `NumberFormatUtil.format_float_fast(value, 5, …)` and had no way to configure it. Java's `PDAbstractContentStream` builds a US-locale `NumberFormat` with grouping off and `setMaximumFractionDigits(4)` in its constructor, and `writeOperand(float)` formats through `NumberFormatUtil.formatFloatFast(real, formatDecimal.getMaximumFractionDigits(), buffer)`, falling back to `formatDecimal.format` when the fast formatter refuses the value. All three classes now carry `@maximum_fraction_digits = 4` with `#maximum_fraction_digits`/`#=` (Java's setter is protected; exposed here as a documented extension), `#format_number` passes it to the fast formatter and uses it for the fallback (`"%.#{digits}f"`), so generated drawing operators now match Java byte for byte (`1.0/3.0` → `0.3333`, `586.46997` → `586.47`). New spec `spec/pdfbox/pdmodel/page_content_stream_number_format_spec.cr` (4 examples): the 4-digit default, a configured 2-digit width, ties rounding away from zero (`±0.5` with zero digits → `±1`, matching `NumberFormatUtil`), and integers/whole floats written without a fraction (`2`, not `2.0`). Four appearance-stream assertions in `spec/pdfbox/pdmodel/interactive/annotation/annotation_spec.cr` were pinned to the old 5-digit output and now assert the Java form (`0.2778`, `586.47`, `209.26 128.32`, `0.7071 0.7071 -0.7071 0.7071`). Full suite 2,813→2,817 examples, 0 failures; the `PDAbstractContentStream.setMaximumFractionDigits`/`writeOperand` rows and the three `NumberFormatUtil` method rows are closed (the `MAX_FRACTION_DIGITS`/`POWER_OF_TENS*` const rows stay `missing` per the const-row convention).
- **`Document#document_information` is never nil (2026-10-29, test-first)**: fixed the documented loose end that killed metadata on in-memory documents. Java's `PDDocument#getDocumentInformation` lazily adds `/Info` to the trailer, wraps it in a `PDDocumentInformation` and caches the wrapper; the port returned `nil` whenever the trailer had no `/Info` — and `nil` for everything in a `Document.create`, because it has no trailer at all. `Document#document_information` now has the Java contract: it returns a `DocumentInformation` (non-nil), creates the trailer through a new `Document#trailer=` setter (which links the `Cos::DocumentState` to it like `COSDocument#setTrailer`), adds an empty `/Info` dictionary when the trailer has none, and caches the wrapper in `@document_information`; `set_document_information(nil)` still removes `/Info` (an extension over Java's NPE) and the next access recreates an empty dictionary. Call sites that defended against the old nil were simplified: `Splitter#create_new_document` copies the (possibly empty) entries unconditionally, `PDFMergerUtility#merge_information` merges into the lazily created destination dictionary, and `pdf_text_2_html` drops its `try`. New examples in `spec/pdfbox/document_information_spec.cr` (+3): an in-memory document gets a cached information dictionary whose title/author survive a save and reload, a document whose trailer has no `/Info` gains one on first access, and repeated calls return the same cached wrapper (previously a new wrapper each time); `spec/pdfbox/document_spec.cr` now asserts the Java behaviour after clearing (`set_document_information(nil)` → empty dictionary, not nil). Full suite 2,808→2,813 examples, 0 failures; the `PDDocument.getDocumentInformation`/`setDocumentInformation` rows are closed. Documented divergence: `set_document_information(nil)` clears instead of throwing, and accessing metadata on a `/Info`-less document dirties the trailer (Java marks `/Info` through `COSDictionary#setItem` too).

- **Incremental save of encrypted documents (2026-10-28, test-first)**: `save_incremental` no longer falls back to a full rewrite when the document is encrypted — the appended revision is encrypted like a full save and the file stays incremental. `Writer#write_incremental` passes `@will_encrypt`/`@security_handler` to the revision's `COSWriter`, so every rewritten string and stream is encrypted with its object key, and `write_incremental_trailer_references` repeats `/Encrypt` (an indirect reference to the existing encryption dictionary) in the new trailer — and in the `/Type /XRef` stream dictionary when the source uses one, which itself stays unencrypted (PDF 32000-1 7.5.8.2). Fixed a latent lifecycle bug this exposed: `Writer#initialize` used to call `prepare_document_for_encryption` for every encrypted document, which re-keys the security handler; for an incremental save that made the new objects decryptable only with a key the existing `/O`//`/U` no longer match (reloading the signed/saved file failed with `InvalidPasswordException`). The preparation now happens in `Writer#write` (full save only), matching Java `COSWriter#write`, which calls `prepareDocumentForEncryption` only when `!incrementalUpdate`; an incremental save reuses the key the document was decrypted with. New spec `spec/pdfbox/pdfwriter/incremental_save_encrypted_spec.cr` (2 examples, AES-128): a classic-xref-table file and an xref-stream file each keep the encrypted source as the verbatim prefix, repeat `/Encrypt`, keep the rewritten `/Info` title out of the appended bytes in plaintext (proving the strings are encrypted), and reload with the password showing the new `/MediaBox` and title. Upstream has no unit test for this path (`TestCreateSignature`'s encrypted variants need a JKS keystore and CMS), so the examples pin the byte-level contract. Full suite 2,806→2,808 examples, 0 failures; the `COSWriter.doWriteTrailer` row is closed and the `COSWriter.write`/`doWriteXRefInc` notes now cover the encrypted path.
- **PDFieldTree (2026-10-28, test-first)**: ported Java's `PDFieldTree` class so the AcroForm field tree has the Java shape instead of a rebuilt `Array`. `Pdfbox::Pdmodel::Interactive::Form::PDFieldTree` includes `Enumerable(PDField)` (Crystal's counterpart of Java's `Iterable`; the tree itself is deliberately **not** an `Iterator` so it can be walked again), rejects a nil AcroForm with Java's `IllegalArgumentException` message (`ArgumentError` — "root cannot be null"), and hands out a `PDFieldTree::FieldIterator` per traversal (Java `PDFieldTree#iterator` returning its `PDFieldTree.FieldIterator`). The iterator is a real pull-based `Iterator(PDField)` (`next` → field or `stop`) that enqueues the tree in parent-before-children order in its constructor and then pops from a `Deque` — exactly Java's `FieldIterator` (queue filled in the constructor, `ArrayDeque` drained by `next`). That eagerness is load-bearing: a lazy walk would change the duplicate semantics (top-level fields are enqueued even when the same dictionary is reachable as a kid; a fully lazy stack yielded 3 fields on the PDFBOX-4131-0 fixture where Java yields 4), so the port keeps the eager queue. The PDFBOX-5044 guard is the identity set on COS dictionaries (`/Kids` reachable twice is logged at error level and skipped), because a `PDField` object is created anew on every lookup. `PDAcroForm#get_field_tree` returns the tree (Java `getFieldTree`), `#field_iterator` returns `PDFieldTree#each` (Java `getFieldIterator()` = `new PDFieldTree(this).iterator()`), and `flatten()` copies the tree with `.to_a` exactly like Java's `flatten()` builds a `List` for the list overload. The old private `walk_field_tree` array walker is gone. New spec `spec/pdfbox/pdmodel/interactive/form/pdfield_tree_spec.cr` (7 examples): nil root, parent-before-children order (`parent`, `parent.kid1`, `parent.kid2`), re-iteration, `field_iterator` order matches the tree, a duplicated kid dictionary yielding each field once, a pull-based `FieldIterator` consumed through `next` (and re-obtainable from `each`), and an early `break` that does not consume the rest of a later pass; the ported upstream `PDFieldTreeTest#test5044` (vendored `PDFBOX-4131-0.pdf`, 4 fields) passes through the new type. Full suite 2,799→2,806 examples, 0 failures; the `PDFieldTree`/`FieldIterator` source rows and the `PDAcroForm.getFieldTree`/`getFieldIterator`/`flatten` rows are closed.
- **Incremental save with an explicit object set (2026-10-28, test-first)**: added the second Java overload `Document#save_incremental(io, objects_to_write : Enumerable(Cos::Dictionary))` (Java `PDDocument#saveIncremental(OutputStream, Set<COSDictionary>)`), for callers that know exactly which objects they touched: the listed dictionaries are appended even when nothing is flagged through `COSUpdateInfo#setNeedToBeUpdated`, which keeps the revision minimal — the documented use case is editing a signed file without invalidating the signature. `Writer#write_incremental(objects_to_write)` (Java `COSWriter(OutputStream, RandomAccessRead, Set<COSDictionary>)`) unions the listed dictionary ids into the computed write set (`incremental_write_ids`), so listing an already-changed object writes it once and the rest of the document stays untouched (`COSWriter#addObjectToWrite`/`#doWriteObjects` are represented by that write set and the object write loop; there is no object queue). - **External signing (2026-10-28, test-first)**: PDFs can now be prepared for an external signature service and completed with its CMS signature, matching Java `PDDocument#saveIncrementalForExternalSigning`. `Document#add_signature(sig, options)` (Java `addSignature(sig, null, options)`; the `SignatureInterface` overload stays unported because there is no CMS implementation) reserves `/Contents` (`SignatureOptions#preferred_signature_size`, else `DEFAULT_SIGNATURE_SIZE` 0x2500) and the `/ByteRange` placeholder `[0 1000000000 1000000000 1000000000]`, then builds the AcroForm wiring: `/AcroForm` created or reused, `/SigFlags` `SignaturesExist`+`AppendOnly`, the `/Fields` entry, a `PDSignatureField` (or the existing field holding that signature dictionary), its widget with the Print flag, a zero-sized `/Rect` plus an empty `/AP /N` stream for invisible signatures, and the widget appended to the page `/Annots` (re-assigned so it stays a direct object). Divergences (documented at `Writer#write_incremental_for_external_signing` and `Document#prepare_visible_signature`): the visual-signature template is searched through its annotations and signature fields instead of Java's COS object pool, `content` returns `Bytes` instead of an `InputStream`, and `set_signature` keeps the Java name with an `# ameba:disable Naming/AccessorMethodName` comment.
