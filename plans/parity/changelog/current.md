- **Clipping: `W`/`W*` now restrict painting (2026-10-29, test-first)**: clipping was ignored. `PageDrawer#clip` was an empty method and no paint path consulted a clip, so `W`/`W*` (and the `q ... W n ... Q` idiom every real page uses) painted outside their region. The clip now lives where Java keeps it, on the graphics state: `PDGraphicsState#clipping_paths` is the list of paths added by `W`, `intersect_clipping_path` adds one with Java's lazy copy-on-clone (`isClippingPathDirty`, so `q` does not copy the list), and `clone` shares the list and re-arms the copy, exactly like `PDGraphicsState#clone`. The path representation is the new `Pdfbox::Util::ClipPath` (AWT-free stand-in for Java's `Path2D` + `Area`): all subpaths of one `W` share one winding rule — so a nested rectangle is a hole under `WIND_EVEN_ODD`, not a second intersection — and `contains?` casts a +x ray across every subpath with the half-open vertex rule. `PageDrawer#clip` builds that path from the current (device-space) path without consuming it, matching Java's `linePath` handling, and every painter now tests the clip through `clipped_at?` (Java's `getCurrentClippingPath().contains`): `fill_span` (fills, glyph fills), `bresenham` (strokes) and `draw_image`. The per-pixel test is an explicit loop over the path list with an unclipped fast path, so pages without `W` pay one array check per span/line instead of a closure allocation per pixel. Divergences (documented at `clipping_paths` and `clip`): Java seeds the initial clipping path from the page crop box (`new PDGraphicsState(page.getCropBox())`) while the port starts with an empty list, because the raster is already the crop box and bounds-checked; and `adjustClip`'s downscale workaround (PDFBOX-4583/4949) has no rasterizer equivalent. New specs: `spec/pdfbox/rendering/clipping_spec.cr` (5 examples, red→green: 4 failed, painting ran past the clip) pins that a fill stops at the clip edge, `q`/`Q` restores the clip, `W*` leaves the even-odd hole, strokes are clipped too, and two successive `W`s intersect; `spec/pdfbox/util/clip_path_spec.cr` (4 examples) pins the geometry helper — inside/outside, even-odd hole, same-direction nested subpaths solid under non-zero, and an area-less path containing nothing. Full suite 2,859→2,868 examples, 0 failures.
- **Real area fills in `PageDrawer` (2026-10-29, test-first)**: fills were outlines. `PageDrawer#fill_path` called `draw_filled`, which simply ran the bresenham line walker over the path (`# simplified: fill using line drawing`), so a filled rectangle was an empty contour, a filled glyph was its outline, and the winding rule was ignored. `fill_path(winding_rule)` and `fill_and_stroke_path(winding_rule)` now rasterize the area like Java's `PageDrawer#fillPath` (`linePath.setWindingRule(windingRule)` then `Graphics2D#fill(shape)`): the new `collect_fill_edges` flattens the device-space path into edges (curves through the existing `bezier_segments`, open subpaths implicitly closed as `Graphics2D#fill` does), and `fill_area` runs a scanline fill — for each device row it collects the edge crossings with the half-open vertex rule, sorts them by x and paints the spans that `inside?` reports, so `WIND_NON_ZERO` (`f`/`F`, rule 0) accumulates edge directions while `WIND_EVEN_ODD` (`f*`/`B*`, rule 1) toggles per crossing. `fill_span` samples pixel centres (`x + 0.5`) and clips to the raster, and the row range comes from the path's y extent, which keeps glyph fills cheap. `fill_and_stroke_path` fills with the non-stroking colour and then strokes with the stroking colour, and glyph rendering (`show_font_glyph` → `fill_path(0)`) now paints solid outlines instead of their contours. The dead `draw_filled` helper is gone. Divergences (documented at `fill_area`): no antialiasing — Java enables it for non-rectangular paths and disables it for rectangular ones (PDFBOX-2302), the port has a hard-edged rasterizer — and stroke width/joins are still ignored. New spec `spec/pdfbox/rendering/path_fill_spec.cr` (6 examples, red→green: the first five failed with the interior transparent): the interior of `0 0 100 100 re f` is inked while the outside is not, a triangle half-plane is filled on one side only, nested subpaths drawn in the same direction are solid under `f` but holey under `f*`, `B` fills the centre with the non-stroking colour while the path edge carries the stroking colour, and a zero-height path paints nothing. Full suite 2,853→2,859 examples, 0 failures.
- **Glyph rendering: `PDFStreamEngine#showGlyph` dispatch + unified graphics state (2026-10-29, test-first)**: `PDFRenderer`/`PageDrawer` drew no text at all — `PDFStreamEngine#show_glyph` was a no-op, so `PageDrawer#show_font_glyph` was dead code (it even called non-existent `font.path`/`font.glyph_name`), and `PDFGraphicsStreamEngine` kept a second `@graphics_state_stack` of `PDGraphicsState` that the parent's text machinery never read, leaving `font` nil in the state the engine actually used. `PDFStreamEngine` now ports Java faithfully: a `create_graphics_state` factory (overridden by `PDFGraphicsStreamEngine` to push the Java-shaped `PDGraphicsState`) feeds the single `@graphics_stack` (typed `Array(GraphicsState | PDGraphicsState)` for the lighter engine), `save_graphics_stack`/`restore_graphics_stack` replace the ad-hoc `@graphics_stack.as(Array).map(&.clone)` snapshotting, `show_glyph` dispatches to `show_type3_glyph` for `PDType3Font` and to `show_font_glyph` otherwise (both now declared on `PDFStreamEngine` only, as in Java, instead of abstract on the graphics engine), and `show_type3_glyph`'s default walks the charproc through the new `process_type3_stream` (TRM replaces the CTM, concatenated with the charproc matrix, text matrices reset, no bbox clip — PDFBOX-1917). `PageDrawer#show_font_glyph` renders the real outline: `PDVectorFont#get_normalized_path` (null/empty paths are skipped, like `GlyphCache#getPathForCharacterCode`) transformed glyph→text→device space via the new `Util::Matrix#transform_point`, then filled/stroked per the text rendering mode, and `show_type3_glyph` delegates to `super` so Type 3 charprocs paint. `PDGraphicsState#text_matrix`/`#text_line_matrix` are no longer nil (Java `new Matrix()`) and the text-state accessors used by the engine (`character_spacing`, `word_spacing`, `horizontal_scaling`, `text_leading`, `text_rendering_mode`, `text_rise`, `font`, `font_size`) were added with Float64/Int32 types so both state classes answer the same messages. The unified stack also restored Java's `processStream` semantics (state saved and restored around each content stream), which exposed three real pre-existing bugs, all fixed against the Java source: `Overlay#createOverlayStream` wrote the affine matrix in the wrong order (`h 0 0 v 1 0 cm` instead of Java's flattened `1 0 0 1 h v`), `Overlay#createOverlayFormXObject` had the 90°/270° `Matrix` cases swapped (90 must be `0 -1 1 0 0 width`, 270 `0 1 -1 0 height 0`), and Java's `adjustRotation`/`createAdjustedLayoutPage` path (PDFBOX-6049) was missing entirely (now implemented with `rotatedDefaultOverlayPagesMap` caching). Fixing those exposed the last one: for PDFs with object streams, `Parser#parse_pages_from_catalog` resolved the page tree through its own `resolve_object`, bypassing the shared `object_from_pool`, so every page dictionary existed twice and page edits were dropped on save — the writer emitted the catalog-tree copy while `Overlay` mutated `document.pages` (new `resolve_page_tree_node` resolves kids through the pool). Specs: `spec/pdfbox/contentstream/glyph_dispatch_spec.cr` (3 examples; red: `undefined method 'show_type3_glyph'`), `spec/pdfbox/contentstream/type3_glyph_spec.cr` (2 examples; red: `Expected [] to eq [72]`), `spec/pdfbox/rendering/text_rendering_spec.cr` (3 examples: a `Tj` leaves the glyph outline on the raster at the text position, a text-free page stays blank, and `1 0 0 rg` fills the glyph in the non-stroking colour — the raster starts as transparent black, so "ink" requires `alpha > 0`), plus the two `graphics_operator_names_spec.cr` SCN/scn examples reworked to observe the colour *during* the stream (Java's `processStream` restores the state, so post-run inspection was only ever passing thanks to the stray stack). Full suite 2,839→2,853 examples, 0 failures; `PDFStreamEngine` showGlyph/showFontGlyph/showType3Glyph/processType3Stream, `Matrix.transformPoint`, the `Overlay` overlay-stream/form-matrix/adjust-rotation rows, the `Parser` page-tree rows and the `OverlayTest#testRotatedOverlays*`/`#testOverlayOnRotatedSourcePages` test rows are closed.
